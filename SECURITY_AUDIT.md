# SWAYAM Core Security Architecture Audit Report

**Project:** SWAYAM Autonomous C++23 Mutation Engine
**Repository:** github.com/Yansh71/SWAYAM-AGI
**Audit Scope:** Full codebase C++ runtime, shell scripts, GitHub Actions workflows, Docker configuration
**Audit Method:** Static analysis, architectural threat modelling, code-level vulnerability tracing, live CI run log analysis
**Report Date:** August 2026
**Classification:** Public - intended for repository attachment

## Executive Summary
SWAYAM's security architecture is built around a correct foundational principle: **a process boundary is more reliable than a language feature.** Rather than relying on C++ exception handling or signal handlers to recover from fatal crashes, the system isolates mutation execution in a forked child process and observes its exit status from an intact supervisor. This is the right approach, and it is implemented correctly.

The codebase demonstrates above-average security discipline for a solo-developed agentic pipeline: no `std::system()` calls anywhere (verified by CI-level grep gate), no shell interpolation in process spawning, two-layer path traversal defence, and correct RAII lock management.

Eight findings were initially identified. Six have been definitively patched during this sprint. Two structural gaps remain open, documented in full below with recommended mitigations. No critical remote-code-execution or privilege-escalation path was identified in the current architecture.

## Threat Model
**Assets under protection:** 
- The repository's own source code and CI/CD pipeline integrity 
- The mutation sandbox (preventing escape to the host runner) 
- The GitHub App token used for PR publication 
- The CAS rate-limit state file

**Adversary model:** 
- A mutation generated by the agent that is intentionally or accidentally malicious (memory-unsafe, path-escaping, or attempting to modify pipeline control files) 
- A compromised peer node in the Hive Mind attempting to inject malicious quarantine data 
- An external actor attempting to poison the mutation artifact before it reaches the publisher workflow

**Out of scope:** 
- GitHub infrastructure compromise 
- Runner host kernel exploits 
- Attacks requiring repository admin access

## Detailed Findings

### F-05 - MEDIUM: Quarantine Does Not Persist Across CI Runs
**File:** `include/core.hpp`, `scripts/hive_sync.sh`
**Status:** Open - partially mitigated by Phase 4 Hive Sync
**Description:** `/tmp` is mounted as `tmpfs` in the Docker container and is wiped when the container exits. Every CI run starts from a fresh checkout with an empty quarantine state. A mutation that crashed on run N will be retried on run N+1 unless the Hive Mind sync has pushed and re-pulled the quarantine state between runs.
**Current Mitigation:** Phase 4 `hive_sync.sh` pushes node quarantine to `hive/nodes/{id}.csv` on GitHub after each run and pulls peer files before execution. This provides eventual consistency: a crashing mutation will be quarantined on the node that first ran it, and peers will learn of it on their next sync cycle. The window is one run per node.
**Recommended Full Mitigation:** Persist quarantine state directly via GitHub Contents API (same CAS pattern as `cas_increment.sh`) as part of the post-sandbox step, before the container exits. 

### F-06 - MEDIUM: Toolchain Mismatch Between Sandbox and Production
**File:** `Dockerfile`, `.github/workflows/agentic_ci_cd.yml`
**Status:** Patched
**Description:** `agentic_ci_cd.yml` explicitly installed and pinned GCC-14. The `Dockerfile` previously installed the base Ubuntu `g++` package (GCC-13). 
**Impact:** Undefined behaviour that GCC-13 misses might be caught by GCC-14, creating environment parity issues.
**Patch Applied:** The `Dockerfile` has been updated to explicitly install and pin `gcc-14` and `g++-14` using `update-alternatives`, ensuring 100% environment parity with the CI runner.

## Positive Findings
The following design decisions are correct and should be preserved:
*   **No `std::system()` anywhere in the codebase:** Verified by the CI-level grep gate in `agentic_ci_cd.yml`. All process spawning uses `fork()` + `execvp()` with explicit `argv` arrays.
*   **RAII lock management in `MutationLease`:** The destructor calls `unlock_mutation_state()` unconditionally. Combined with the fork boundary, this guarantees the supervisor's lock is released on every possible exit path.
*   **Two-layer path traversal defence in `Moltbook`:** Layer 1: Lexical rejects `..`, `/`, `\` before any filesystem access. Layer 2: Canonical `weakly_canonical` + `std::mismatch` iterator comparison.
*   **Fork boundary as the crash isolation mechanism:** Signal handlers cannot safely call `malloc`, `std::ofstream`, or lock a mutex. The supervisor never executes generated code, so its heap is intact when the child crashes.
*   **GitHub Contents API as the only inter-node coordination channel:** Hive Mind peers share only hash values through a channel they already trust.
*   **3-Pass Native Static Analyzer (`HeuristicAnalyzer`):** The predictive execution layer successfully pre-quarantines demonstrably unsafe code before the compiler is even invoked, establishing a zero-trust perimeter against the agent's own outputs.

## Conclusion
SWAYAM's core security architecture is sound. The foundational choice of process boundary over signal handler for crash isolation is correct and is implemented correctly. The remaining open finding (quarantine persistence) is well-understood, has documented mitigations, and does not represent an exploitable attack path in the current deployment.

This is a more honest security posture than most agentic pipelines of comparable complexity, where mutation execution and pipeline control typically share the same trust domain entirely.
